# hub を動かす無料クラウド候補の調査

静かなら止まり、リクエストが来たら立ち上がる（scale-to-zero）無料サービスの比較

> 📅 作成: 2026-09-19 / 更新: 2026-09-24

[⌂](../../README.md)

## 1. 調べた観点

- **scale-to-zero**: 待受け中は課金・稼働ゼロで、リクエストが来たら自動起動するか
- **永続化**: identities・tokens（[全体構想](../10_plan/p260919-01-全体構想.md)参照）を保存し続けられるDBが、無料のまま持つか
- **クレジットカード要否**: 個人利用として登録の敷居
- **コード変更の要否**: 素のNode.jsプロセスのまま動くか、専用ランタイム（Workers等）への書き換えが要るか

> [!NOTE]
> <strong>単純なGCE/EC2を除外する理由。</strong>常時起動の仮想マシンは「静かにしていても課金され続ける」ため、今回の狙い（休んでいれば無料）に合わない。

## 2. 候補比較

| 候補 | 方式 | 無料枠 | クレカ | コード変更 | 注意点 |
|---|---|---|---|---|---|
| **Google Cloud Run** | コンテナ、scale-to-zero | 月200万リクエスト・36万vCPU秒 等（常時無料枠） | ⚠️ **要** | ✅ **不要** （Dockerでそのまま） | 永続ディスクが無いため、DBは外部サービスに出す必要がある |
| Google Cloud Functions (2nd gen) | 関数、scale-to-zero | Cloud Runと同一基盤・同等の無料枠 | ⚠️ **要** | ⚠️ **一部** （ハンドラ形式に合わせる） | 実体はCloud Run。単体で選ぶ理由は薄い |
| Cloudflare Workers + Durable Objects | V8アイソレート（エッジ）＋Durable Objects（SQLite内蔵ストレージ） | Workers無料枠＋DO無料枠（日次10万リクエスト、1GBまで） | ✅ **不要** | ❌ **要** （Node.jsの長時間プロセス前提コードは書き直し） | WebSocketはDurable Objectsが無料プランでも使える（訂正: 当初「別料金」と見ていたが、無料プランでも利用可） |
| Render（Freeプラン） | コンテナ、15分無操作でスリープ→次リクエストで起動（約1分） | 750インスタンス時間/月 | ✅ **不要** | ✅ **不要** | 無料PostgreSQLは作成30日で失効。DBは別途用意が要る |
| Fly.io | コンテナ | ❌ **実質無し** （無料トライアルのみ） | — | — | 2024年以降、新規アカウントの無料枠は廃止済み。候補から除外 |
| Turso（libSQL） | DBのみ（SQLite互換） | 情報が資料間で食い違う（無料枠ありとする記事と、Hobbyが月$9有料化したとする記事が混在） | — | — | **要再確認**。契約前に公式ダッシュボードで現在の条件を必ず見る |

<strong>裏取りの状況。</strong>Cloud Run・Cloud Functions・Cloudflare（Workers/D1/Durable Objects）・Render は公式ドキュメントで確認済み。Fly.io も公式コミュニティ情報で確認済み（無料枠が無いこと）。Turso は情報源同士が矛盾しており、未確認として扱う。

## 3. プッシュ通知はできるか

「静かにしていれば止まっているサーバーから、後で通知が飛んでくる」ことができるかという問いには、**誰への通知か**で答えが変わる。

### 3.1 エージェント間の通知（project-id・instance-id宛て）

これは [全体構想](../10_plan/p260919-01-全体構想.md) の Messaging フェーズで使う、いわゆる ai-chat-lite の `wait`（長時間ポーリング）と同じ話になる。「サーバーが止まっている間に通知する」のではなく、**クライアント側が接続を持ち、その接続が来た時点でサーバーが起きて応答する**形になる。

| 候補 | 長時間接続の可否 | 備考 |
|---|---|---|
| Google Cloud Run | ✅ **可** | WebSocket・HTTP長時間接続に対応（GA）。タイムアウトは既定5分、最大60分まで延長可。切れたら再接続する前提の設計にする |
| Cloudflare Workers + Durable Objects | ✅ **可** | Durable Objects は無料プランでもWebSocketを扱える。インスタンスごとに状態（＝待受け中のカーソル位置）を保持できるので、instance_id単位のwaitと相性がよい |
| Render（Free） | ✅ **可** | 普通のNode.jsプロセスなのでWebSocket・長時間HTTPともそのまま動く。ただしスリープからの初回接続は約1分のコールドスタートが乗る |

> [!NOTE]
> <strong>「本当のゼロ」ではない。</strong>待受け中の接続がある間はそのインスタンスは起きている（＝課金対象になり得る）。ai-chat-liteの`wait`が240秒ごとに区切って張り直す設計にしてあるのは、この種の環境でも扱いやすくするためでもある。

### 3.2 人間の端末への通知（スマホ・デスクトップ）

こちらは仕組みが根本的に違う。**hub自身が起きていなくても送れる。** Web Push（VAPID）やFCM・APNsは、ブラウザ・OSベンダーが運用する仲介サーバーに一度メッセージを預ける方式で、hubは「送りたくなったときだけ短時間起きて、仲介サーバーにPOSTする」だけでよい。受け手の端末は常時接続を保つ必要がなく、hubも常時起動している必要がない。

> [!NOTE]
> <strong>scale-to-zeroとの相性がよい。</strong>エージェント間通知（3.1）が「待つ側が接続を保つ」方式なのに対し、人間向け通知は「送る側が起きた瞬間に済ませる」方式なので、hubが眠っている時間が長いほど有利という、この構想の狙いと一致する。

<strong>今回のスコープには含めない。</strong>認証・セキュリティ基盤（MVP）にもロードマップの各フェーズにも今のところ登場しない。将来、人間への通知（レビュー依頼・障害通知等）を作る段になったら、Web Push採用を検討する。

## 4. 所感（決定ではない）

| 方針 | 組み合わせ | 向いている場面 |
|---|---|---|
| A. コード変更を避ける | Render（Free） ＋ 外部DB（要選定） | 今の設計（Node.js＋SQLite想定）をほぼそのまま動かしたい。ただしDBの永続先は別途決める必要がある |
| B. 無料枠の厚さを取る | Google Cloud Run ＋ Firestore等の外部DB | クレジットカード登録は許容でき、長く動かす前提なら最も無料枠が手厚い |
| C. クレカ不要を徹底する | Cloudflare Workers ＋ Durable Objects | 個人の検証用途に割り切り、hubをWorkers向けに書き直す前提を受け入れる。WebSocketも無料枠内で使える |

> [!NOTE]
> <strong>まだ選ばない。</strong>本書はロードマップの「4. LAN/クラウド対応」フェーズで使う調査であり、MVP（認証・セキュリティ基盤）の実装先には影響しない。どの方針にするかは、そのフェーズの計画時に改めて決める。
