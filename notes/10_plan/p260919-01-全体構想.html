背景と全体構想

MVP（Minimum Viable Product）とは、実用最小限の製品のこと。構想の全部を一度に作らず、まず動く最小限の一部分だけを作って試す考え方。本書では「認証・セキュリティ基盤」を最初のMVPとし、メッセージングやファイル受け渡しは含めない。

1.1 目指すもの

複数のAIエージェント（Claude Codeセッション等）が、プロジェクトフォルダ名から取った :project-id: を宛先・送信元の識別子として使い、次のことをできるようにする。

  • エージェント間のメッセージ通信
  • エージェント間のファイル受け渡し
  • 認証・アクセス制御によるセキュリティの強化
  • ローカルPC・LAN内サーバー・クラウドサービスのどこでも動く配置の柔軟性
  • （将来）Mattermostのような運用中チャットの巻き取り
  • （将来）Redmineのようなチケット管理
構想は大きく、最初は小さく。すべてを一度に作らず、後から積み増せる土台から着手する。

1.2 既存資産との関係

ai-chat-lite（ローカルPC内のAI間チャット、Node.js＋SQLite、ポート常駐サーバー）が既にエージェント間メッセージングの実運用を持っている。ai-agent-support を将来的な統合・置き換え先とする方向で考えるが、今回のMVPでは ai-chat-lite には一切手を入れない。認証・セキュリティ基盤を独立したモジュールとして作り、統合の判断は基盤が固まってから改めて行う。

1.3 進め方の原則

原則内容
段階分割認証基盤 → メッセージング → ファイル受け渡し → LAN/クラウド対応 → 外部連携、の順に積む
後方互換より前方設計今回作る認証層は「今は使わないメッセージング・ファイル・チケットの各モジュールが後から乗る」ことを前提にインターフェースを決める
他プロジェクト不可侵ai-chat-lite・Mattermost・Redmineの実体は直さない。連携は外側から行う
OS非依存Windows・Mac・Linuxのどこでも同じコードで動く（2.4節参照）
エージェント非依存Claude Code・Codex等の特定のエージェント製品に依存しない。エージェント種別は固定の許可リストを持たず、名乗った略称をそのまま受け付ける（2.2節参照）
ネット接続に依存しない外部の認証局・SaaS・DNS解決に頼らず、閉域網（インターネットに繋がらないLAN）だけでも身元登録から認証までが完結する。将来ローカルLLMでエージェントを動かす運用を見込む

2.2 身元の粒度: instance_id を主キーにする

ai-chat-lite が避けていた問題。project-id（プロジェクトフォルダ名）は一意にならない。同じプロジェクトで Claude Code を2つ以上起動することも、Claude Code と Codex を同時に起動することも実際に行われる。project-id を身元の主キーにすると、複数セッションが同じ鍵を共有する（または後から起動した方が上書きする）ことになり、1セッションの侵害が他の正常なセッションまで巻き込んで失効させる原因になる。

そこで身元の主キーは起動ごとに生成する instance_id とし、project_id は「どのプロジェクトの代理か」を示すラベルとして登録時に添える二階層構成にする。同じ project_id に複数の instance が共存でき、失効も instance 単位で行える。

エージェント種別の略称

instance は登録時に、project_id に加えて自分がどのエージェントかを略称で名乗る。

略称エージェント
ccClaude Code
cxCodex
agAntigravity CLI

一覧に無いエージェントは、小文字英数字2〜4文字程度の略称を新たに名乗ってよい（hub側で固定の許可リストは持たない）。instance_id 自体は project_id + agent_type + 起動ごとの乱数 から組み立てる（例: ai-agent-support#cc#a3f9）。

「#」の意味はここでは区切り文字。リソース抽象化構想の行範囲指定（#L1-20）とは別の用法であり、:project-id: と組み合わせて書くのは行範囲指定の方だけなので、実際の記述上で両者が混在することはない。

2.3 認証の仕組み（MVPの中心）

  1. 起動した instance は鍵ペア（Ed25519）をローカルで生成する。秘密鍵はそのマシンのユーザープロファイル配下に置き、Gitには入れない
  2. project_id・agent_type・公開鍵を hub（認証サーバー）に登録する（register）。hub が instance_id を発行して返す
  3. 接続時、hub がチャレンジ（乱数）を渡す。クライアントは秘密鍵で署名して返す（login）
  4. hub は署名を公開鍵で検証し、短命の署名付きトークン（JWT相当。project_id と instance_id の両方を含む）を発行する
  5. 以降、メッセージング・ファイル受け渡し等の各モジュールは、このトークンをそのまま「どのプロジェクトの、どのインスタンスからのリクエストか」の根拠として使う（各モジュールが個別に鍵を扱わずに済む）
パスワードやAPIキーの平文共有を避ける。秘密鍵はマシンから出さず、hub には公開鍵と署名しか渡らない設計にする。

2.4 配置の考え方

hub（認証サーバー）は接続先（--port か --url）を変えるだけで、同じコードのまま3つのトポロジーに対応する。

トポロジーhub の置き場所使う場面
同一PC内localhost 上のhub（例: 127.0.0.1:8890）1台のPC内で複数プロジェクト・複数instanceが相互通信する、最も基本の形
LAN内LAN内の1台をhubにし、各PCがそのIP・ホスト名へ接続同じ拠点内の複数PCにまたがる相互通信
クラウドクラウド上の1台をhubにし、各PCがドメイン経由で接続拠点をまたぐ相互通信。家・会社などネットに繋がる開発環境間で使う
閉域網（インターネット非接続）LAN内の1台をhubにし、外部への通信を一切行わない将来、ローカルLLMでエージェントを動かす運用。クラウドAPIに頼らずLAN内だけで完結させたい場合
4つは「どこにhubを置くか」の違いでしかない。project・instance側のコードは接続先の設定を変えるだけで、実装を分けない。LAN・クラウドでは通信が信頼できない経路を通るため、認証（2.3節）に加えてTLSによる経路の暗号化を必須にする。閉域網では外部の認証局・NTP・DNS等に頼れないため、hub自身が鍵の発行から検証まで自己完結できることを前提にする（2.3節の設計はこの前提を満たす）。

今すぐ全部には対応しないが、後から動かせるように分けておく。

配置MVPでの対応後の対応方針
同一PC内（Windows）対応そのまま
同一PC内（Mac）未対応Node.js標準APIの範囲に留め、Windows固有処理（レジストリ・SJIS等）を作らない
LAN内未対応bindアドレスとTLS設定を外出しにするだけで到達できる作りにする
クラウド未対応鍵・DBの保存先を環境変数で差し替え可能にする。OS依存処理を作らない

この方針を守るため、MVPの実装言語は Node.js（TypeScript優先。ts > mjs > cjsの順、共通ルール「使用言語（Node / Bun）」に従う） を採用する（Windows/Mac/Linuxで同一コードが動き、ai-chat-lite との将来統合にも支障がない）。

最初のMVP: 認証・セキュリティ基盤

3.1 スコープ

含む含まない（次フェーズ以降）

短命トークンの発行・検証・instance単位の失効Mattermost/Redmine連携
CLIでの動作確認手段Webの管理画面

3.2 想定するCLI（動作確認用・仮）

agentauth keygen :project-a: --agent-type cc     # 鍵ペアを生成しローカルに保存
agentauth register :project-a: --agent-type cc -p 8890
                                                  # 公開鍵をhubに登録し instance_id を受け取る
agentauth login <instance_id> -p 8890            # チャレンジに署名し、トークンを取得
agentauth verify <token> -p 8890                 # トークンの有効性を確認（動作確認用）
agentauth revoke <instance_id> -p 8890           # そのinstanceだけを失効させる

3.3 データモデル（案）

テーブル主な列
identitiesinstance_id, project_id, agent_type, public_key, registered_at, revoked_at
tokenstoken_id, instance_id, project_id, issued_at, expires_at, revoked_at

3.4 完了の判定基準

  • 同じ project_id・異なる agent_type（例: cc と cx）で2つの instance を登録し、それぞれ独立した instance_id が発行される
  • 正しい秘密鍵で login するとトークンが発行される
  • 他人の instance_id を名乗って login しようとすると拒否される（署名検証で弾く）
  • 発行したトークンが有効期限切れ後に verify で拒否される
  • 同一 project_id 内の一方の instance だけを revoke しても、もう一方の instance は使い続けられる
  • テストが `tools/40_test/` から一括実行できる
